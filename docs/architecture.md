# Архитектура

Как устроен сервис и почему именно так.

## Общая картина

```
SourceCraft API          git                AppSec API
      │                   │                     │
      └───────────┬───────┴─────────────────────┘
                  ▼
        движок оценки (C#)
        ┌─────────────────────────┐
        │ сбор фактов  →  расчёт  │
        └─────────────────────────┘
                  │
            JSON-отчёты
                  │
                  ▼
            SQLite  →  сайт (Python)
```

Два сервиса и один договор между ними — JSON-отчёт. Движок ничего
не знает про сайт, сайт ничего не знает про то, как считается
оценка.

## Почему два языка

Это не прихоть, а разделение по характеру работы.

**Движку** нужны параллельная работа с тысячами репозиториев,
запуск внешних процессов, строгие типы для методики, где легко
перепутать проценты с долями. C# с его задачами и проверкой типов
на этапе сборки подходит лучше.

**Сайту** нужны быстрые страницы и простые формы. FastAPI и Jinja
дают это без церемоний.

Граница между ними — файл отчётов. Каждую половину можно заменить
целиком, не трогая вторую.

## Движок

| Проект | Ответственность |
| --- | --- |
| `RepoHealth.Contracts` | описание фактов и отчёта — общий язык |
| `RepoHealth.Collection` | сбор данных из API и git |
| `RepoHealth.Scoring` | методика расчёта |
| `RepoHealth.Api` | движок как служба |
| `RepoHealth.Cli` | те же операции из терминала |
| `RepoHealth.Worker` | периодический обход каталога |

### Сбор отделён от расчёта

Это главное архитектурное решение.

Сбор ходит в сеть, запускает git, ошибается по таймауту и зависит
от прав. Расчёт не делает ничего из этого: на входе факты,
на выходе отчёт.

Следствия:
- методику можно проверять тестами без сети и без токенов;
- одни и те же факты всегда дают одну и ту же оценку;
- изменив методику, можно пересчитать всё заново, не скачивая
  репозитории повторно;
- ошибка сбора не превращается в плохую оценку — она превращается
  в честное «нет данных» с причиной.

### Факты — это память

Файл фактов на каждый репозиторий хранит и данные, и дату
обновления проекта на момент сбора. Отдельного хранилища состояния
нет: при следующем обходе мы сравниваем сохранённую дату с текущей
и пропускаем то, что не менялось.

### Как читается git

Репозиторий не выгружается на диск. Клонируем с `--no-checkout`
и историей за год, затем читаем нужное командами git:

| Что нужно | Как берём |
| --- | --- |
| файлы в корне | `ls-tree` |
| README | `show HEAD:README.md` |
| история | `log` |
| размеры файлов | `ls-tree -r -l` |
| пометки TODO | `grep -I -c` |

Временная папка удаляется сразу после чтения, в том числе при
ошибке. На диске ничего не накапливается.

## Сайт

| Модуль | Ответственность |
| --- | --- |
| `main.py` | страницы и API |
| `db.py` | хранилище отчётов |
| `importer.py` | загрузка файла отчётов в базу |
| `refresh.py` | слежение за появлением свежих отчётов |
| `auth.py` | вход через Яндекс ID |
| `sourcecraft.py` | личный разбор через движок |
| `markdown_report.py` | выгрузка отчёта |

Сайт не считает оценки и не ходит в SourceCraft за данными
каталога. Его дело — показать готовое.

## Два потока данных

### Публичный рейтинг

```
воркер → обход каталога → факты → расчёт → reports.jsonl
                                                │
                                      сайт замечает изменение
                                                │
                                             SQLite → страницы
```

Идёт по расписанию, служебным токеном, без участия пользователя.
Сайт проверяет файл отчётов раз в минуту и переливает его в базу
сам.

### Личный разбор

```
пользователь → Яндекс ID → кабинет → свой токен
                                        │
                              движок: сбор + расчёт
                                        │
                              таблица личных разборов
```

Идёт по запросу, с токеном пользователя, и видит то, что видит
он сам: закрытые репозитории, свои проверки безопасности, свои
сборки.

## Работа с секретами

**Токен пользователя живёт только в памяти процесса.** Он не
попадает ни в базу, ни в журналы, ни в файлы. Перезапуск сервиса
разлогинивает всех — для прототипа это правильный размен.

**Токен не попадает в отчёт.** При разборе закрытого репозитория
токен подставляется в адрес для клонирования, а git охотно
повторяет адрес в сообщениях об ошибках. Поэтому перед записью
любое сообщение чистится от токена.

**Личные разборы лежат отдельной таблицей.** Не фильтром в общей,
а именно отдельной: среди них бывают закрытые репозитории, и в
публичной витрине им не место. Структурная гарантия надёжнее
условия в запросе, которое однажды забудут написать.

**Служебный токен передаётся только окружением.** Ни в аргументах
команд, ни в коде, ни в образе.

## Почему SQLite

Для прототипа: файл рядом с приложением, ничего не нужно ставить.
Запросы написаны так, чтобы переезд на PostgreSQL не потребовал
их переписывать. При нынешних объёмах — 24 тысячи отчётов — SQLite
справляется с запасом.

## Запуск

```
proxy   ─ обратный прокси, сертификат
engine  ─ движок как служба
worker  ─ периодический обход
web     ─ сайт
```

Наружу смотрит только прокси. Собранные факты и база лежат в томе
и переживают пересборку образов.
